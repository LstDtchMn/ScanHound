## 2. The outage (no diff — operational)

Every file in `C:\Tools` had an empty, protected DACL; the DIRECTORY was
healthy. Windows refused to LAUNCH dovi_tool/ffmpeg/ffprobe/MediaInfo. DV
detection was dead ~12 hours; the detector recorded `[WinError 5]` against
~3,900 MEDIA files, which reads as a drive fault — every media file was in fact
readable. The denial was on CreateProcess, and the giveaway is that the error
text names no file (an `open()` PermissionError includes the path).

Cause proven from the artifact, since object-access auditing and script-block
logging are both off:

    D:PAI(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;0x1200a9;;;BU)

`P` = inheritance removed, three hand-written `OICI` ACEs. Every normal folder
on the box is unprotected with 11-13 inherited ACEs. So: a lockdown of the form
`icacls C:\Tools /inheritance:r /grant "...:(OI)(CI)F" /T`. On the DIRECTORY the
inherit flags are valid; on each FILE `/inheritance:r` stripped the inherited
ACEs and inherit-only grants added nothing back.

Repaired with `/inheritance:e`, verified functionally (dovi_tool 2.3.1 runs; a
previously-denied title extracts an RPU reporting Profile 7 FEL). 3,769 rows
whose only error was this outage were reset. Then IMMUNISED: each file now
carries its own explicit ACEs, so `/inheritance:r` (which removes only inherited
entries) cannot strip them — **proven by replaying the destructive command
verbatim against a copy**: 4 ACEs survived and the binary still ran.

*Question: is per-file explicit ACEs the right hardening, or does it create a
maintenance trap where a future intentional permission change to the directory
silently fails to reach the files?*

Also found: **two scheduled tasks** were scanning the whole library in parallel
(4-hourly from the repo wrapper, 6-hourly from a pinned copy) since 11 Aug —
days of duplicated disk work on 50-70 GB files. Jesse retired one. This also
corrects an earlier claim of mine that the pinned wrapper "is what runs": both
ran, from different copies.

## 3. #72 — the label sync must not claim it observed a file

The scheduled DV auto-sync gates on `MAX(last_seen_at)` for `source='scan'` and
records a PRE-sync watermark, but `sync_labels`' rating_key back-write stamped
`last_seen_at = CURRENT_TIMESTAMP`. Each sync pushed the gate metric past its
own watermark: **11 full-library reconciles in 14 hours** against a detector
producing rows twice a day; three added zero labels.

`upsert_dv_scan` grows `observed=True/False`; `observed=False` preserves
`last_seen_at` and the sig columns. Tests pin `last_seen_at` to a fixed past
value first — `CURRENT_TIMESTAMP` has one-second granularity, so wall-clock
drift would have made the suite pass on the bug at random.

*Questions:* (a) is preserving `last_seen_at` right, or should the WATERMARK
move to the post-sync value instead? I chose the former because `last_seen_at`
means "a scanner saw this file" and the labeler is not a scanner — but the
alternative is one line in `app_service` and touches no shared DB semantics.
(b) Does any consumer legitimately depend on the back-write refreshing it? I
found none; this is the assertion I am least sure of.

## 4. #75 / #76 — the Kometa tag set

Final set: `DV FEL` / `DV MEL` / `DV8` / `DV5`, plus `DV7` (Profile 7 spans two
badges), `DV` (any DV), and `HDR10`. Reconciliation moved from "everything
managed except THE label" to set arithmetic — the old form could only express
one tag per title, so a correct second tag was always classified stale.

`RETIRED_LABELS = {"DV P8","DV P5"}` stays inside `MANAGED` **so the sync can
remove them**. Dropping them instead makes the labeler blind and strands a
stale `DV P8` on every Profile 8 title forever. That mutation passed 58 tests
before I added two for it.

`HDR10` cannot come from `dv_scan` — it has no HDR axis; `none` means "no DV
found", equally true of an HDR10 remux and a plain SDR 4K file. It requires an
authoritative `none` AND Plex's own bt2020 flag. A rating_key ABSENT from that
index is UNKNOWN, not False, and unknown never authorises removal.

*Questions:* (a) `MANAGED` now contains the bare tag `DV` — the broadest name
yet and the most likely to collide with a hand-applied label. The closed-set
intersection protects user labels and a test pins `DV Cut` surviving; is that
sufficient? (b) The first sync after merge strips `DV P8`/`DV P5` from ~220
titles before Kometa re-runs. Accepted by Jesse, but is there a safer ordering?

## 5. #77 — the JDownloader stall (found in the last hour)

`poll_results` had `except Exception: return []` around the reconnect. When JD
restarted, the poller failed **silently** every few seconds for ~15 hours; the
enclosing loop logs at `debug`, off in production. Noticed only because the
downloads list stopped changing. Jesse reports this recurring.

The fix tracks the ABSENCE OF SUCCESS rather than any failure mode: last-success
time, failure streak, last error; WARNING rate-limited to one per 5 minutes;
`/health` exposes `jd_poll` and `jd_enabled`; the scheduled host checker alerts
via Gotify at 30-minute cadence.

*Questions:* (a) is 30 minutes the right threshold, given the poller runs every
few seconds? (b) Liveness is recorded where JD ANSWERS rather than at the end of
`poll_results`, so a parsing bug cannot masquerade as an outage — is that the
right seam? (c) **I have not established WHY the reconnect kept failing** — the
cache invalidation and 90s TTL look correct, so a fresh `_connect_jd_device()`
should have re-authenticated. The silence is fixed; the underlying cause is
still unproven, and that is the gap I most want a second opinion on.
