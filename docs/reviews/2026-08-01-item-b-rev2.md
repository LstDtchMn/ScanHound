## 2. Classification is now evidence-driven

You were right, and the flaw was worse than a naming problem: rev 1 named disk
state as its primary axis and then derived it from exception type. `classify_failure()`
now takes a `DiskObservation` — what the caller saw when it looked — and every
field defaults to `None` meaning *not established*. An incomplete observation
yields `UNKNOWN`.

Cause is still derived from the exception, because a cause is worth counting,
but it no longer decides safety. There is a test asserting that a
`FileNotFoundError` yields `UNKNOWN`, not `UNCHANGED` — the precise inference
you flagged.

One consequence worth surfacing: **a present destination requires a completeness
verdict before any conclusion is drawn.** "The destination exists" is not a
state; "the destination exists and is verified complete" and "…and is not" are
opposite states, and rev 1 could not tell them apart.

## 3. The state model, with your two missing states

```
UNCHANGED                     source present, destination absent
DEST_PARTIAL_SOURCE_PRESENT   unverified destination, source intact
DEST_COMPLETE_SOURCE_PRESENT  DUPLICATED — copy finished, source not consumed
DEST_COMPLETE_SOURCE_ABSENT   completed on disk
SOURCE_ABSENT_DEST_UNUSABLE   CATASTROPHIC — original gone, nothing usable
PRIOR_OCCUPANT_DISPLACED      an overwrite displaced the previous occupant
UNKNOWN                       not established
```

Source presence and destination completeness are independent, which is what
makes duplication and loss distinguishable at all.

* only `UNCHANGED` is retry-safe;
* only `DEST_PARTIAL_SOURCE_PRESENT` is mechanically cleanable;
* everything else requires an operator;
* `is_catastrophic` is its own property, so the loss case cannot be handled as
  generic `UNKNOWN`.

## 4. Not a marker — a pre-operation evidence snapshot

You were right that a "started" marker resolves nothing, and this is the part I
would have got wrong: my instinct was a post-commit marker, which has the same
defect one step later.

The intent now records source size, mtime and `dev:inode`, whether the
destination already existed, the prior-occupant reference, temp path, method,
expected postcondition and an idempotency token. `reconcile_interrupted()`
compares that against the filesystem now and yields a `DiskObservation` that
feeds straight into the classifier.

Verified against real files — an interrupted operation resolves to a specific
state rather than an open question:

| what happened after the intent | resolves to |
|---|---|
| nothing | `UNCHANGED` |
| the move completed | `DEST_COMPLETE_SOURCE_ABSENT` |
| copy finished, source left | `DEST_COMPLETE_SOURCE_PRESENT` |
| destination truncated | `DEST_PARTIAL_SOURCE_PRESENT` |
| source consumed, nothing landed | `SOURCE_ABSENT_DEST_UNUSABLE` |

There is also a test for a **different file at the source path**: same path,
different size, must NOT count as intact. Treating it as the original is how a
reconciliation lies, and it is the case I would most expect a naive
implementation to get wrong.

## 5. Cardinality enforced by the database

`kind IN ('intent','outcome')` as a CHECK, plus partial unique indexes for one
intent and one outcome per operation, and a unique `event_uuid`. Four tests
insert violating rows through raw SQL and require `IntegrityError` — the model
is no longer something the writer is trusted to honour.

`operation_uuid` is now separate from `event_uuid`. Rev 1 overloaded one column
for both the row identity and the operation correlation, which is precisely why
"one intent per operation" could not be written as a constraint.
